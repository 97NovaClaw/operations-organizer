CRITICAL ISSUES ENCOUNTERED AND SOLUTIONS:
==========================================

1. AJAX HANDLER REGISTRATION TIMING ISSUE
------------------------------------------
PROBLEM: AJAX handlers were being registered during page rendering instead of WordPress initialization
SYMPTOM: All AJAX requests returned "0" (WordPress default for unknown actions)
ROOT CAUSE: 
- AJAX handlers were registered in features/stream-dashboard/index.php (line 38)
- This file is only loaded during page rendering
- AJAX requests are processed in separate request lifecycle where these handlers weren't available

SOLUTION:
- Moved AJAX handler registration to operations-organizer.php (global scope)
- Added: OO_Stream_Dashboard_AJAX::init(); after other AJAX registrations
- Removed duplicate registration from features/stream-dashboard/index.php

LESSON: AJAX handlers must be registered during WordPress initialization, not page rendering

FILES AFFECTED:
- operations-organizer.php (added global AJAX init)
- features/stream-dashboard/index.php (removed local AJAX init)

2. INCORRECT METHOD CALLS TO NON-EXISTENT CLASSES
--------------------------------------------------
PROBLEM: AJAX handlers calling methods on OO_Stream_Dashboard_DB that don't exist
SYMPTOM: 500 Internal Server Error after successful nonce verification
ROOT CAUSE:
- Code was calling OO_Stream_Dashboard_DB::add_phase() 
- But add_phase() method exists in OO_DB class, not OO_Stream_Dashboard_DB
- Similar issues with update_phase(), delete_phase(), toggle_phase_status(), etc.

SOLUTION:
Changed method calls from OO_Stream_Dashboard_DB to OO_DB:
- OO_Stream_Dashboard_DB::add_phase() → OO_DB::add_phase()
- OO_Stream_Dashboard_DB::update_phase() → OO_DB::update_phase()
- OO_Stream_Dashboard_DB::get_phase() → OO_DB::get_phase()
- OO_Stream_Dashboard_DB::delete_phase() → OO_DB::delete_phase()
- OO_Stream_Dashboard_DB::toggle_phase_status() → OO_DB::toggle_phase_status()

LESSON: During refactoring, verify that all method calls point to classes where methods actually exist

FILES AFFECTED:
- features/stream-dashboard/ajax.php (multiple method call corrections)

3. NONCE MISMATCH BETWEEN FRONTEND AND BACKEND (STREAM DASHBOARD SPECIFIC)
-----------------------------------------------------------------------
PROBLEM: JavaScript sending nonces with different keys than backend expected
SYMPTOM: 400 Bad Request errors with "Nonce verification failed"
ROOT CAUSE:
- JavaScript was using oo_data.nonces.add_phase
- But PHP was providing nonces as oo_data.nonce_add_phase
- Two different nonce structures were being created in operations-organizer.php

SOLUTION:
- Standardized on individual nonce properties (nonce_add_phase, nonce_edit_phase, etc.)
- Updated JavaScript to use correct property names
- Removed duplicate/conflicting nonce structures

LESSON: Maintain consistent naming conventions between frontend and backend data structures

NOTE: This issue was specific to the stream dashboard modular architecture. Simple embedded 
JavaScript (like customer autocomplete in job-management-page.php) works fine with the 
standard nonce localization pattern and doesn't require this level of complexity.

FILES AFFECTED:
- operations-organizer.php (nonce structure cleanup)
- features/stream-dashboard/assets/js/main.js (nonce property name corrections)

4. MISSING JQUERY UI SORTABLE DEPENDENCY
-----------------------------------------
PROBLEM: Drag-and-drop phase reordering failing with "sortable is not a function"
SYMPTOM: JavaScript error preventing sortable functionality
ROOT CAUSE: jquery-ui-sortable dependency not enqueued

SOLUTION:
- Added 'jquery-ui-sortable' to wp_enqueue_script dependencies
- Corrected wp_localize_script target script name

LESSON: Always verify JavaScript dependencies are properly enqueued

FILES AFFECTED:
- operations-organizer.php (script enqueuing)

5. INACTIVE PHASES APPEARING IN PHASE LOG ACTIONS
--------------------------------------------------
PROBLEM: Deactivated phases still showing in "Phase Log Actions" tab
SYMPTOM: Users could start/stop jobs on phases that should be inactive
ROOT CAUSE:
- Phase filtering logic only checked stream_id and includes_kpi
- Missing check for is_active status

SOLUTION:
Added is_active filter to phase selection logic:
```php
// OLD:
if ($phase_item->stream_id == $current_stream_id && !empty($phase_item->includes_kpi))

// NEW:
if ($phase_item->stream_id == $current_stream_id && 
    !empty($phase_item->includes_kpi) && 
    !empty($phase_item->is_active))
```

LESSON: When filtering data for UI display, ensure all relevant status fields are checked

FILES AFFECTED:
- features/stream-dashboard/views/tab-log-actions.php

6. MODAL FORMS EMPTY AFTER REFACTORING
---------------------------------------
PROBLEM: Edit/Add phase modals opened but contained no form fields
SYMPTOM: Buttons worked but forms were empty placeholders
ROOT CAUSE: Modal HTML was not properly copied from original template

SOLUTION:
- Restored complete modal form HTML from original template
- Standardized modal IDs to match JavaScript selectors
- Ensured all form fields and nonce fields were present

LESSON: When modularizing, ensure all HTML dependencies are properly migrated

7. KPI EDIT MODAL & ACTIVATION LOGIC
----------------------------------------
PROBLEM: 
1. Unchecking a phase in the "Edit KPI" modal did not unlink it upon saving.
2. The "Activate" checkbox would only deactivate a KPI; it could not reactivate it.

SYMPTOMS:
- Phase links remained unchanged in the database regardless of checkbox state.
- A checked "Active" box was ignored on save, and the KPI would become inactive.

ROOT CAUSES:
1. **Missing Context in AJAX Call:** The form was not sending the `stream_id` context, so the backend logic couldn't determine which stream's phase links to modify.
2. **Incorrect Checkbox Serialization:** Standard jQuery `serialize()` does not include unchecked checkboxes. When the "Active" box was checked, it sent `is_active=1`. When unchecked, it sent nothing, which the PHP backend interpreted as `is_active=0` (the default). The fix for deactivating worked, but activating didn't, pointing to a deeper issue.
3. **Flawed DB Query with Optional JOIN:** The `ajax_update_kpi_measure` handler called `OO_DB::get_phase_kpi_links_by_measure` with `join_phases` set to `false`. However, the DB method's `ORDER BY` clause still referenced the alias (`p.phase_name`) for the un-joined table. This caused a fatal SQL error, the query returned `[]` (an empty array), and the application logic incorrectly concluded the KPI had no links, automatically deactivating it as a safety measure.

SOLUTIONS:
1. **Added `stream_id_context` to Form Data:** Modified the AJAX submission in `main.js` to include the current stream ID, giving the backend the necessary context.
2. **Explicit Checkbox Handling:** Updated the `main.js` form submission logic to read the `is_active` checkbox's checked property (`.prop('checked')`) and explicitly add `is_active=1` or `is_active=0` to the data sent to the server. This ensures the value is always present.
3. **Made DB Query `ORDER BY` Clause Conditional:** Refactored the `get_phase_kpi_links_by_measure` method in `class-oo-db.php`. The `ORDER BY` clause now intelligently selects columns based on whether the `join_phases` argument is true or false, preventing the SQL error.

LESSONS:
- Client-side forms must always provide sufficient context (like stream/page IDs) for backend processing.
- Never trust default browser form serialization for checkboxes; always handle their state explicitly in JavaScript to ensure a value is consistently sent.
- Database methods with optional `JOIN`s must have logic to handle cases where the join is not performed, especially in `ORDER BY` or `WHERE` clauses that reference the optional table. A silent SQL error can lead to baffling application-level bugs.

FILES AFFECTED:
- `features/stream-dashboard/assets/js/main.js` (Added stream_id context and explicit checkbox handling)
- `features/stream-dashboard/ajax.php` (Corrected logic to use the right DB methods for fetching links)
- `includes/class-oo-db.php` (Made the ORDER BY clause in `get_phase_kpi_links_by_measure` conditional)

OVERARCHING THEMES & META-LESSONS FOR FUTURE DEVELOPMENT:
=========================================================

After completing this extensive refactoring project, several high-level patterns and themes emerged that transcend the specific technical issues. These meta-lessons should guide future development work:

## 1. THE "PORTING PATTERN" - A Systematic Approach to Refactoring

**THE PATTERN:**
When moving functionality from monolithic to modular architecture, we discovered a reliable 3-step process:
1. **Identify the Source** - Find the working implementation in the old system
2. **Map the Dependencies** - Trace all connections (AJAX handlers, nonces, database methods, JavaScript events)
3. **Port Systematically** - Move each piece while maintaining the exact same interfaces

**WHY THIS WORKS:**
- Reduces the risk of breaking functionality during refactoring
- Provides a clear checklist for completeness
- Makes debugging easier by isolating what changed vs. what stayed the same

**ANTI-PATTERN TO AVOID:**
Trying to "improve" the code while refactoring. This leads to multiple variables changing simultaneously, making it impossible to isolate the source of bugs.

## 2. THE "CHECKBOX SERIALIZATION TRAP" - A Recurring Issue

**THE PATTERN:**
We encountered the same checkbox handling bug THREE times:
- KPI Measures activation checkbox
- Derived KPI activation checkbox  
- Phase "includes KPI" checkbox

**THE ROOT CAUSE:**
JavaScript's `serialize()` method doesn't include unchecked checkboxes, but backend PHP code often uses `isset()` to check for checkbox values. This creates a mismatch where:
- Checked: Sends `field=1`, `isset()` returns `true` → Works
- Unchecked: Sends nothing, `isset()` returns `false` → Works
- BUT when you explicitly send `field=0`, `isset()` still returns `true` → Breaks

**THE UNIVERSAL FIX:**
```javascript
// WRONG:
var formData = $(this).serialize();

// RIGHT:
var formData = $(this).serializeArray();
var isActiveChecked = $form.find('[name="is_active"]').prop('checked');
formData.push({name: 'is_active', value: isActiveChecked ? '1' : '0'});
```

```php
// WRONG:
'is_active' => isset($_POST['is_active']) ? 1 : 0,

// RIGHT:
'is_active' => isset($_POST['is_active']) ? intval($_POST['is_active']) : 0,
```

**LESSON:** This is a systematic issue that will recur. Create a standard pattern and apply it consistently across all checkbox handling.

## 3. THE "CONTEXT PROBLEM" - Why Modular Systems Need More Data

**THE PATTERN:**
Multiple bugs were caused by insufficient context being passed between frontend and backend:
- KPI phase linking needed `stream_id_context`
- Modal forms needed current stream information
- AJAX handlers needed to know which stream they were operating on

**THE ROOT CAUSE:**
Monolithic systems have implicit context (everything operates on "the current page"). Modular systems lose this implicit context and must pass it explicitly.

**THE SOLUTION PATTERN:**
Always include contextual identifiers in AJAX requests:
```javascript
formData.push({name: 'stream_id_context', value: oo_data.current_stream_id});
formData.push({name: 'return_to_stream', value: streamSlug});
```

**LESSON:** When modularizing, audit every interaction to ensure sufficient context is being passed.

## 4. THE "NONCE NAMING CHAOS" - Consistency as a Debugging Tool

**THE PATTERN:**
Nonce mismatches were a recurring source of 403 errors. The issues were always subtle naming inconsistencies:
- Frontend: `oo_data.nonce_edit_phase` vs Backend: `oo_edit_phase_nonce`
- Frontend: `oo_data.nonces.add_phase` vs Backend: `oo_data.nonce_add_phase`

**THE SOLUTION:**
Establish and enforce a strict naming convention:
- **Frontend:** Always `oo_data.nonce_{action}_{entity}`
- **Backend:** Always `oo_{action}_{entity}_nonce`
- **Creation:** Always `wp_create_nonce('oo_{action}_{entity}_nonce')`

**LESSON:** Naming consistency isn't just aesthetics—it's a debugging tool. Inconsistent naming makes bugs harder to spot and fix.

## 5. THE "AJAX LIFECYCLE TRAP" - Understanding WordPress Request Flow

**THE PATTERN:**
The most fundamental bug was AJAX handlers returning "0" because they weren't registered properly.

**THE ROOT CAUSE:**
Misunderstanding WordPress's request lifecycle:
- Page rendering: Loads page-specific files
- AJAX requests: Separate lifecycle, only loads globally registered handlers

**THE SOLUTION:**
AJAX handlers MUST be registered during WordPress initialization (`init` hook), not during page rendering.

**LESSON:** Understand the framework's request lifecycle. Don't assume page-rendering logic applies to AJAX requests.

## 6. THE "PROGRESSIVE DEBUGGING STRATEGY" - From Broad to Specific

**THE EFFECTIVE PATTERN:**
1. **Network Level:** Check if AJAX request reaches the server (200 vs 0 vs 403 vs 500)
2. **Handler Level:** Verify the correct handler is being called (logging at function start)
3. **Authentication Level:** Check nonce verification (logging nonce values)
4. **Data Level:** Examine the data being processed (logging $_POST contents)
5. **Database Level:** Verify database operations (logging query results)
6. **Response Level:** Check what's being returned (logging response data)

**WHY THIS WORKS:**
- Isolates the problem to a specific layer
- Prevents wasting time debugging the wrong component
- Provides a systematic approach when multiple things could be wrong

**LESSON:** Don't debug randomly. Follow the data flow systematically from frontend to backend.

## 7. THE "FEATURE ISOLATION PRINCIPLE" - Modular Architecture Best Practices

**THE PATTERN:**
Successful modularization required clear boundaries:
- Each feature has its own AJAX handlers
- Each feature has its own database methods
- Each feature has its own JavaScript files
- BUT features share common infrastructure (nonces, base classes, utilities)

**THE BALANCE:**
- **Isolate:** Feature-specific logic
- **Share:** Infrastructure and utilities
- **Standardize:** Interfaces between modules

**LESSON:** Modular architecture requires discipline about what gets shared vs. what stays isolated.

## 8. THE "DEBUGGING INFRASTRUCTURE INVESTMENT" - Tools That Pay Off

**WHAT WORKED:**
- Extensive logging with searchable prefixes (`[EXTREME_DEBUG]`)
- Frontend console logging for AJAX requests
- Systematic error handling with meaningful messages
- Version tracking for iterative debugging

**THE PAYOFF:**
Initial time investment in debugging infrastructure paid massive dividends when complex bugs arose.

**LESSON:** Invest in debugging infrastructure early. The time spent setting up logging saves exponentially more time during debugging.

## 9. THE "REFERENCE IMPLEMENTATION STRATEGY" - Keep the Old System Running

**THE PATTERN:**
Instead of replacing the old system immediately, we kept both systems running in parallel and used the old system as a reference implementation.

**THE BENEFITS:**
- Could compare behavior side-by-side
- Had a working example to copy from
- Could verify that refactored functionality matched original behavior

**LESSON:** During refactoring, preserve the original implementation as long as possible. It's your best debugging tool.

## 10. THE "INCREMENTAL COMPLEXITY PRINCIPLE" - One Variable at a Time

**THE PATTERN:**
Most successful debugging sessions involved changing only one thing at a time and testing immediately.

**THE ANTI-PATTERN:**
Making multiple changes simultaneously and then trying to figure out which change fixed or broke something.

**THE DISCIPLINE:**
- Change one thing
- Test immediately  
- Commit if it works
- Revert if it breaks
- Repeat

**LESSON:** Resist the urge to fix multiple things at once. Incremental progress is faster than debugging complex interactions.

## 1. High-Level Job Overview Dashboard (Kanban & Gantt)

**CONCEPT:**
A high-level dashboard to visualize the status of all streams for a single job. This would serve as a "macro" view for project managers.

**KANBAN VIEW:**
- **Board:** Represents one `oo_jobs` record.
- **Columns:** Generic, static statuses (e.g., 'Pending', 'In Progress', 'Completed').
- **Cards:** Each stream assigned to the job (records from `oo_job_streams_link`). A job with 3 streams would have 3 cards on this board.
- **Logic:** The card's position in a column would be determined by the **existing** `status_in_stream` column in the `oo_job_streams_link` table. No database changes would be needed for this view.

**GANTT VIEW:**
- **Chart:** A timeline visualization for one `oo_jobs` record.
- **Rows:** Each stream assigned to the job.
- **Timeline Bars:** The start and end points of the bars would be determined by the **existing** `start_date_stream` and `due_date_stream` columns in the `oo_job_streams_link` table. No database changes would be needed.

**IMPLEMENTATION NOTE:**
This would likely be a new feature module (`features/job-overview/`) and would provide an alternative view to the detailed, single-stream Phase Kanban. This is a future goal after the core Phase Kanban is implemented.
